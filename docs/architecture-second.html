Architectural Insights

평가에서 드러나지 않은 두 가지 구조적 발견.

⚠ 1. 이중 draft 시스템 (중복)

두 개의 평행한 chat/draft 구현이 공존한다. UI는 homepage-drafts 쪽만 쓰고, ChatAction을 가진 chat-homepage-sessions 쪽은 사실상 연결돼 있지 않다.

ChatAction schema 강제(45%)가 약한 진짜 이유 — schema와 로직은 chat-homepage-sessions.ts에 있는데, 실제 사용 경로는 ChatAction을 안 거치는 homepage-drafts.ts다.

사용 중: lib/homepage-drafts.ts → /api/homepage-drafts/*
미연결: lib/chat-homepage-sessions.ts → /api/chat-homepage-sessions/*
권장: 하나로 통합 후 ChatAction을 단일 경로에 강제

⚠ 2. 비동기 인프라가 끊겨 있음

완전한 job queue가 이미 있다 — jobs/{pending,processing,completed,failed}, batch worker, per-job report, batch-run-report까지. 하지만 웹 POST /api/homepage-generation-jobs는 이 큐를 무시하고 직접 builder를 spawnSync한다.

즉 Async Job(45%)·Polling(40%)의 핵심 부품은 이미 작성돼 있고, 배선만 하면 된다.

존재: scripts/run-pending-homepage-jobs.mjs (worker)
존재: scripts/create-homepage-job.mjs (enqueue helper)
끊김: API → jobs/pending 으로 쓰지 않음
05

Next Priorities

부합도를 가장 크게 올릴 3개. 모두 신규 빌드보다 기존 자산 연결/정리에 가깝다.

1

Generation Job 비동기화 45% → 80%+

POST에서 spawnSync 제거 → jobs/pending에 저장 후 즉시 queued 반환. worker는 기존 run-pending-homepage-jobs.mjs 상시 실행. Flow 3·4 동시 해결.

// app/api/homepage-generation-jobs/route.ts - const result = spawnSync("bash", ["scripts/run-homepage-builder.sh", requestPath]) - status: "running" + fs.writeFileSync(`jobs/pending/${jobId}.json`, JSON.stringify(requestBody)) + status: "queued" // 즉시 반환, build 대기 없음
2

단일 chat 경로 + ChatAction 강제 45% → 75%+

이중 시스템을 하나로 통합. Goose/deterministic 응답을 모두 ChatAction으로 정규화하고 schema로 검증한 뒤에만 적용.

// 허용 action만 통과 type ChatAction = | ask_missing_info | patch_draft | toggle_section | change_layout | run_generation + validateChatAction(action) // schemas/chat-action.schema.json
3

customer / debug 응답 분리 50% → 80%+

고객용엔 status · homepage_url · preview_available만. provider·model·runLog·validation_report는 debug 블록으로.

{ "ok": true, "customer": { status, homepage_url, preview_available }, "debug": { provider, validation_result, build_result, agent_run_report_path } }
